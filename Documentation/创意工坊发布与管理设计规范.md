# 创意工坊发布与管理设计规范

创意工坊发布与管理是 Blueprint 系统的作者侧全屏空间，用于把多个“我的蓝图”组合成一个可发布的工坊内容，并管理草稿、已发布版本与后续更新。

它不替代 Blueprint Workspace 中的“创意工坊”来源筛选。两者职责必须分开：

- Blueprint Workspace 的“创意工坊”来源负责浏览、收藏和使用别人发布的蓝图内容；
- Workshop Publisher 负责作者自己的打包、发布、更新与删除；
- 一个 Workshop Content 可以包含多个 Blueprint，不建立“一张蓝图 = 一个工坊条目”的硬绑定。

## 1. 入口与空间归属

Blueprint Workspace 顶部右侧 Actions 区目标顺序：

```text
[ 创意工坊 ]   [ + 新建蓝图 ]
```

“创意工坊”位于“新建蓝图”左侧，使用 Secondary Action 层级；“新建蓝图”继续保持当前 Primary Action 层级。

点击“创意工坊”：

```text
Gameplay / Blueprint Workspace
→ Workshop Publisher Fullscreen Space
```

Workshop Publisher 使用与 Settings / Load / Save / New Game 相同的 Global Space 视觉母版，不制作加大的 Workspace，也不使用 Blueprint Editor 的 Modal 外壳。

关闭 / Esc：

```text
Workshop Publisher
→ 返回 Gameplay
→ 恢复进入前的 Blueprint Workspace 与筛选上下文
```

正式 UI State 需要保存进入来源，不能依靠 DOM 是否存在推断返回位置。

## 2. 全屏信息架构

第一版稳定一级导航：

```text
创意工坊
├ 发布新内容
├ 草稿
└ 已发布
```

职责：

- **发布新内容**：创建一个新的 Workshop Content Draft；
- **草稿**：继续编辑尚未发布的内容包；
- **已发布**：查看、更新、打开工坊页面或删除已经发布的内容。

不在这里重复制作“浏览创意工坊”。浏览仍留在 Blueprint Workspace 的来源筛选中。

全屏页面复用：

```text
.wanhu-global-space
├ .global-space-header
├ Workshop-specific Body
└ .global-space-footer
```

Workshop 只拥有内容区域 Geometry 与业务状态；Root / Header / Footer 的材质、前景和按钮层级继续由 Global Space Visual System 持有。

## 3. Workshop Content 是蓝图集合

核心关系：

```text
WorkshopContentDraft
├ id
├ title
├ description
├ blueprintIds[]
├ coverBlueprintId
├ tags[]
├ visibility
└ localRevision

PublishedWorkshopContent
├ localContentId
├ providerItemId
├ publishedVersion
├ publishedAt
├ visibility
└ publishedSnapshot
```

稳定规则：

- 一个 Workshop Content 至少包含 1 个 Blueprint；
- 可以包含多个 Blueprint；
- 第一版只允许选择 source=mine 的“我的蓝图”；
- System / Workshop 来源蓝图不能直接被重新打包发布；
- Workshop Content 的标题、描述、标签和可见性属于内容包，不回写单个 Blueprint；
- Blueprint 删除前如果仍被草稿引用，必须给出明确影响提示；已发布版本不因本地 Definition 删除而失效。

## 4. 发布新内容 / 内容包编辑器

“发布新内容”不是传统文件上传表单，而是一个内容包编辑器。

第一版编辑区域：

```text
内容名称
包含蓝图
封面
简介
标签
可见性
```

### 4.1 添加蓝图

“+ 添加蓝图”进入同一个全屏空间内的选择步骤，不调用系统文件选择器。

选择器：

- 只显示“我的蓝图”；
- 复用 Blueprint 4:3 Media Card 视觉；
- 支持多选；
- 已加入当前内容包的蓝图显示明确 Selected；
- 确认后返回内容包编辑器；
- 不新建第二套蓝图数据模型。

### 4.2 封面与预览

第一版不新增 Workshop 专用摄影工具。

- 封面从已包含 Blueprint 的 Preview 中选择；
- 默认使用第一个加入内容包的 Blueprint；
- 其它 Blueprint Preview 构成内容预览画廊；
- 后续确有需求再增加自定义封面 Capture，不能在第一版复制一套 Photography 流程。

### 4.3 草稿

内容包随时可以保存为 Draft。

草稿允许：

- 修改标题、简介、标签、可见性；
- 增加 / 移除 / 调整包含的蓝图；
- 更换封面；
- 删除草稿。

离开存在未保存修改的 Draft 时使用共享 Confirm，不通过 Toast 替代阻塞式决定。

## 5. 已发布内容管理

“已发布”使用适合长列表管理的 Global Space 内容结构，视觉可参考 Save / Load 的大条目，而不是 Catalog 小卡片。

每个已发布内容至少显示：

- 封面；
- 标题；
- Blueprint 数量；
- 可见性；
- 当前发布版本；
- 上次发布时间 / 更新时间；
- 本地是否存在未发布修改。

详情页动作：

```text
打开工坊页面
编辑内容
发布更新
删除工坊内容
```

删除远端内容使用共享 Danger Confirm。

“打开工坊页面”交给 Provider 返回的平台 URL / Overlay 行为；UI 不硬编码 Steam URL 规则。

## 6. 本地修改与发布版本

本地 Blueprint 修改不得自动改变已经发布的 Workshop Content。

稳定流程：

```text
发布 v1
→ 保存 Published Snapshot

本地 Blueprint / Content Draft 修改
→ 标记“有未发布更改”
→ 玩家明确点击“发布更新”
→ 生成并上传 v2 Snapshot
```

因此：

- Published Content 显示的是最后一次明确发布的 Snapshot；
- 本地 Draft 是下一版本编辑态；
- 发布成功后才更新 publishedVersion / publishedSnapshot；
- 发布失败时保留 Draft，不覆盖最后成功版本；
- 不把本地实时 Blueprint 引用当作远端版本权威。

## 7. Provider 边界

UI 不直接依赖 Steamworks。

正式 Unity 边界：

```text
Workshop UI
    ↓
WorkshopService
    ↓
IWorkshopProvider
    ├ SteamWorkshopProvider
    └ Future Platform Provider
```

Provider 负责：

- Create / Update Item；
- 上传内容与 Metadata；
- Visibility；
- 打开平台页面；
- Delete / Unpublish；
- Provider Item Id 与错误映射。

Workshop UI 负责：

- Draft；
- 内容包组成；
- 编辑状态；
- 发布请求；
- 进度 / 成功 / 错误反馈；
- 已发布列表与本地脏状态。

## 8. Web Prototype 边界

Web 第一阶段只验证 UI、数据关系与工作流：

```text
创建草稿
→ 多选我的蓝图
→ 编辑 Metadata
→ 模拟发布
→ 已发布列表
→ 本地修改提示
→ 模拟发布更新
→ 模拟删除
```

不声称已经接入真实 Steam Workshop。

第一阶段不做：

- Steam 登录 / 鉴权；
- 真实上传网络；
- 评论、评分、订阅量统计；
- Workshop 浏览器；
- Workshop 搜索 / 排行；
- 别人的蓝图二次打包；
- 依赖自动解析；
- 自定义工坊封面摄影；
- 平台审核 / 法务流程模拟。

## 9. 状态与退出规则

Workshop Publisher 是顶层 Fullscreen Space，不与 Gameplay Workspace 同屏存在。

进入时：

- 保存 Blueprint Workspace 来源上下文；
- 清理 Hover；
- 暂停当前 Workspace 输入；
- 不销毁 Blueprint Catalog 数据。

退出时：

- 恢复 Gameplay；
- 恢复进入前 Blueprint Workspace 分类 / 规模 / 来源 / 收藏筛选；
- 不因为进入 Workshop Publisher 把用户重新送回“全部蓝图”。

Workshop 内部从 Editor → Blueprint Picker → Editor 属于同一 Fullscreen Space 内部导航，Esc 优先返回上一级，不直接退出整个 Workshop Space。

## 10. 实施工作流

该功能按一个连续工作流拆成三个可验收阶段，不一次把真实 Provider、完整管理与全部视觉塞进一个 PR。

### W3.1 Workshop Fullscreen Shell

目标：

- Blueprint Workspace “新建蓝图”左侧增加“创意工坊”入口；
- 建立 Workshop Fullscreen Global Space；
- 完成“发布新内容 / 草稿 / 已发布”一级导航；
- 建立 Gameplay ↔ Workshop 的来源恢复；
- 不做真实发布。

验收重点：全屏空间家族、入口 / 退出、导航与返回状态。

### W3.2 Workshop Content Editor

目标：

- 新建 Draft；
- 从“我的蓝图”多选；
- 内容名称 / 简介 / 标签 / 可见性；
- 从包含蓝图中选封面；
- 草稿保存、继续编辑、删除；
- 不接真实 Workshop Provider。

验收重点：多蓝图组成一个内容包，选择器不允许 System / Workshop 来源重新打包。

### W3.3 Published Management

目标：

- 模拟发布；
- 已发布列表与详情；
- Published Snapshot；
- 本地“有未发布更改”；
- 发布更新；
- 打开工坊页面动作；
- Danger Delete；
- 定义 IWorkshopProvider 接口边界，但 Web 仍使用 Mock Provider。

验收重点：已发布版本不随本地 Blueprint 自动变化，Draft / Published 权威清楚。

## 11. Unity 映射与所有权

建议正式 Unity 结构：

```text
WorkshopSpace.uxml
├ GlobalHeader
├ WorkshopPrimaryNavigation
├ WorkshopContentHost
└ GlobalFooter

WorkshopContentEditor.uxml
WorkshopBlueprintPicker.uxml
WorkshopPublishedList.uxml
WorkshopPublishedDetail.uxml
```

数据层建议：

- BlueprintCatalog：蓝图 Definition 权威；
- WorkshopDraftRepository：本地内容包草稿；
- WorkshopPublicationRepository：本地已发布 Metadata / Snapshot；
- WorkshopService：发布用例；
- IWorkshopProvider：平台适配。

UI 不直接修改 Blueprint Definition，也不直接调用平台 SDK。
