# Unity 6.6 视觉兼容收尾审查

本审查基于 `main c97af6557eee74d1a81b14321217368e9508f54c`。

目标不是要求 Web CSS 与 USS 逐字一致，而是判断：正式 Web 截图是否已经足够稳定，可以作为 Unity 6000.6.2f1 UI Toolkit 的美术与结构参考；同时识别仍会让 Unity 最终画面明显偏离 Web 的存量。

## 结论

当前项目已经达到“可以开始/继续正式 Unity 6.6 UI Toolkit 实现”的条件，但还不能宣称“Visual Parity 已全部完成”。

已经完成的关键前置：

- W1 五个代表场景 Style Lock 完成：Settings / Building Workspace / Gameplay HUD / Dialog / Color Tool；
- W2 已完成 Loading、City Wall + Gate、Access Stair、Transition Stair、Map View；
- 这些正式截图不再依赖对应模块中的 CSS Gradient / Web-only Shadow / 私有 Filter 才成立；
- Shared Theme / Surface / Controls 已冻结为默认 Owner，Feature 不再顺手重画；
- Build 与 main 六组 UI Review 持续通过；
- 结构性状态标记已经多处改为真实元素，便于映射为 VisualElement。

因此，**Unity 6.6 迁移可以继续，不需要等待 Web 全仓“零 CSS 特性债务”**。

但在宣布 Web 美术完全兼容 Unity 6.6 前，还应完成少量正式视觉收尾。

这些数字不能直接等价为 18/29 个“阻塞项”。需要按视觉职责分类。

## A. 仍需收敛的正式视觉

### 1. Main Menu

主要文件：

- `src/styles.css`
- `src/menu-refine.css`

当前仍有大量正式可见 Gradient：

- Main Menu Shade；
- Menu List 背景；
- Hover / Primary Row 背景；
- 底部分隔衰减；
- 旧/共享 Game Vignette。

这是当前最高优先级。主菜单是正式大面积视觉，不能依赖 Unity 6.6 项目已实测拒绝的 CSS Gradient。

建议后续拆成独立小批：

- Full-screen Shade：共享 PNG / Sprite 或分层纯色 Overlay；
- Menu Row：纯色 Alpha + Border / 真实 Accent Element；
- 底部衰减线：共享小纹理或纯线；
- 不修改菜单布局与交互。

### 2. Blueprint Editor

文件：

- `src/workspace/blueprint-editor.css`

当前仍有：

- 1 个 Linear Gradient；
- 2 个 inset box-shadow；
- 1 个 brightness()。

Blueprint Editor 属于正式玩家工作流，不应依赖 brightness 或 inset shadow 才能成立。

建议以 1–2 Runtime 文件独立收敛。

### 3. Weather Visual

文件：

- `src/gameplay/weather-art-pass.css`
- `src/gameplay/weather-visual-controls.css`

当前仍有：

- 2 个 Linear Gradient；
- 多个 inset / glow / drop-style box-shadow。

天气本身可以由 Unity 世界渲染承担，但这些文件中同时存在正式 UI/Art Pass，因此必须区分：

- 世界天气表现：交给 URP / VFX / World Rendering；
- UI 参数与状态：必须在无 Shadow / Gradient 时仍清楚；
- 如果 Web 截图仍把 Gradient 当作关键 UI 视觉，则继续收敛。

### 4. Full-screen Background / Game Vignette

文件：

- `src/backgrounds.css`
- `src/styles.css`

还有全屏 Gradient Vignette。

这类效果适合复用与 Loading 相同的方向：

- Web / Unity 共用低分辨率 Alpha Texture；
- 或拆成有限纯色 Edge Overlay；
- 不要求在 USS 中模拟 CSS Gradient。

### 5. Map Legend

文件：

- `src/gameplay/gameplay-top-shell.css`

当前 Legend 仍有一条 `linear-gradient` 色带。

Map View 主覆盖层已经 W2.5 收敛，但 Legend 仍是正式 UI。建议改成：

- 小型共享 Texture / Sprite；
- 或有限色块段；
- 不保留 CSS Gradient 作为唯一实现。

## B. 可以保留为 Web Adapter / Unity 世界渲染替代的项目

以下项目不应机械追求 Web CSS = USS：

### Tree Placement

`src/tools/tree-placement/tree-placement.css`

Ring / Tree Ghost 的 box-shadow / drop-shadow 属于 Web 世界预览占位。

Unity 最终应由世界空间 Gizmo / Renderer / Overlay 表达，而不是迁成 USS Shadow。

要求只保留：

- Brush 半径可辨识；
- Single Placement 目标可辨识；
- Selected / Invalid 等状态语义明确。

### Terrain Edit

`src/tools/terrain-edit/terrain-edit.css`

局部 Shadow 属于世界预览辅助表达，可由 Unity 世界空间材质/线框替代。

### Building Selection

`src/selection/building-selection.css`

选中建筑的 Glow/Inset 属于世界对象 Selection Visualization。

Unity 可用 World-space Outline / Decal / Overlay / Renderer Feature 实现；不要求 USS 完全复制。

### Color Tool Lighting / Scheme World Handles

- `src/tools/color-tool/modes/lighting/lighting-mode.css`
- `src/tools/color-tool/modes/scheme/scheme-mode.css`

场景灯光/建筑选择 Handle 属于 Web Adapter。Unity 使用真实对象选择反馈即可。

但面板本身的 Focus / Selected 必须继续遵守共享 Control 基线。

## C. 可接受但需要保持 Fallback 的共享 Enhancement

### Backdrop Blur

最新审计仍统计到 45 个 backdrop-filter 声明，但债务已经限定在 7 个批准文件中。

这不是当前迁移阻塞项，前提保持：

- 没有 Blur 时文字和控件仍可读；
- Blur 不承担 Selected / Focus / Warning 等状态语义；
- 不再增加新的私有 Owner；
- Unity 侧统一使用项目验证后的共享 Blur / 无 Blur Fallback。

### Workspace / Shared Surface Shadow

例如：

- `src/workspace/workspace-world-first-glass.css`

如果 Shadow 只是 Web Enhancement，去掉后 Border / Surface / Layering 仍成立，可保留为 Web 增强；Unity 不需要逐像素复制。

## D. CSS Grid / Pseudo-element / Variable Math

这些统计不能直接作为“必须清零”的目标。

### CSS Grid

118 declarations / 21 files。

迁移原则仍是：布局可拆为 UI Toolkit Flex Row / Column。只有无法拆解的 Grid 才是阻塞项。

### Pseudo-element

82 selectors。

纯装饰允许保留；承担真实状态或结构语义的伪元素需要真实节点。

W1 已处理多个关键 Selected / Tone / Active Marker。后续只继续抓有业务/状态意义的伪元素，不做机械清零。

### CSS math with var()

22 处。

需要按用途判断：

- 仅 Web world-preview 几何：允许 Adapter 化；
- 正式 UITK Geometry：迁移时必须解析成确定值或 C# 设置；
- 不把复杂 CSS Variable Math 原样翻译到 USS。

## 下一阶段：文字布局偏移

用户已经在最新 UI 中观察到文字布局偏移。该问题应独立于 W2 Visual Effect 收敛处理。

下一阶段建议命名为：

**Typography / Text Layout Parity**

重点不是继续调颜色，而是检查 Web 与 Unity TextCore / Font Asset 的真实度量差异：

- Font Asset / fallback 是否一致；
- Baseline 与 ascender / descender；
- line-height；
- font-size 与 glyph 实际 bounds；
- letter-spacing；
- Label / Icon 的 align-items；
- 固定高度控件中文字的垂直居中；
- 中文、数字、英文混排时 fallback 字体是否改变基线；
- 11px / 9.5px 等小字号是否在 Unity 中产生像素取整差异；
- 4K / reference resolution 下是否出现半像素位置；
- TextElement / Label 的 padding 与 Web line box 差异。

这一阶段应优先建立几个代表性 Typography Fixture，再修共享规则，不要逐页面手工把文字向上/向下挪 1–2px。

## 推荐顺序

1. W2.6 审查记录完成；
2. 再做 3–5 个正式视觉小批：Main Menu → Blueprint Editor → Weather → Background/Vignette → Map Legend；
3. audit:unity 重新盘点并冻结 Ratchet；
4. 进入 Typography / Text Layout Parity；
5. 最后再做 Unity 6.6 Player 侧实际截图对照。
