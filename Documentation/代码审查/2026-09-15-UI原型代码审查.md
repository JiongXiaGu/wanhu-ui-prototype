# 2026-09-15 UI 原型代码审查

## 审查目的

记录当前 UI Prototype 的代码结构、合理性、主要债务和后续优化方向，方便后续对话或开发者快速定位，而不是把视觉讨论重新走一遍。

## 当前结构判断

整体架构已经从早期“单页补丁 + DOM 注入”进入正常 React 组件化阶段，核心方向是合理的。

### 已经稳定的部分

#### 1. Gameplay 状态集中

`src/app/ui-state.ts` 集中管理 Gameplay 的 Workspace、Tool、Flyout、Pause、速度、Building Placement 模式和基础历史状态。

优点：

- UI Space 优先级清晰；
- 不再依赖多个组件各自猜当前状态；
- Pause 子页面、Tool 模式和 Flyout 都有明确状态来源；
- 后续扩展 Review Scenario 比较容易。

#### 2. Review Scenario 独立

`src/app/scenarios.ts` 将视觉评审状态与正常交互流程分开。

优点：

- Playwright 可以稳定直达某个 UI 状态；
- 不需要每次通过几十次点击准备截图；
- 视觉回归更可控。

#### 3. 主要功能组件已经拆分

Gameplay、Archive、Settings、Building Workspace、Building Placement、Pause、Flyout 等已经有独立组件目录或文件。

相比早期通过 querySelector / MutationObserver 注入 UI 的方式，维护性已经显著提升。

#### 4. Load / Save 与 Settings 已经复用

- Load / Save 共享 Archive 视觉系统；
- Main Menu / Pause 共享 Settings；
- 没有继续维护两套相似但会逐渐分叉的页面。

这是正确方向。

## 当前主要代码债务

### 1. CSS 仍存在历史层叠

`src/main.tsx` 同时导入：

- `styles.css`
- `workspace.css`
- `tool-overlay.css`
- `menu-refine.css`
- `backgrounds.css`
- `gameplay-refine.css`
- `operation-hints.css`
- 以及较新的组件 CSS。

问题不是文件数量本身，而是部分样式职责来自不同演进阶段，容易出现：

- 同一个组件同时受旧样式和新模块样式影响；
- 修改局部时依赖 Cascade 覆盖历史规则；
- 后续 AI 不容易判断哪一条 CSS 是真正权威来源。

建议：

等视觉语言稳定后再做一次受控 CSS 整理，不要现在立刻大改。

整理目标：

- 全局 Token / Canvas / 通用 Button 保留全局；
- Gameplay 级布局放 Gameplay；
- 组件样式跟随组件目录；
- 删除确认无引用的 refine / legacy 规则。

不要边做视觉设计边同时大规模改 CSS 组织。

### 2. `App.tsx` 仍承担较多顶层 Flow

当前 `App.tsx` 除 Screen 切换外，还直接包含 New Game 的结构、`FlowBackdrop` 与 `PresetCard`。

短期没有问题，但 New Game 下一轮准备重做，届时建议拆为：

- `src/new-game/NewGameScreen.tsx`
- `src/new-game/WorldPresetCard.tsx`
- `src/new-game/new-game.css`

这样 `App.tsx` 只负责顶层 Screen 编排。

### 3. Prototype 数据大量硬编码

Archive、Settings、建筑目录、世界预设等数据目前主要用于视觉验证，因此硬编码可以接受。

后续如果原型需要更复杂交互，应先建立轻量数据模型，而不是直接把更多 if / map 数据继续堆到 JSX 内。

不要为了“架构漂亮”现在提前引入复杂 Store 或后端。

### 4. 历史状态只是视觉模拟

`canUndo / canRedo` 当前是非常轻量的 Prototype 状态，不代表真实 Building Placement History。

最终 Unity 实现不能照搬这个逻辑；实际撤销/重做应由工具运行时历史系统决定。

### 5. Tooltip 尚未正式组件化

项目已经确定大量解释信息进入 Hover Tooltip，但目前正式共享 Tooltip 系统尚未建立。

建议后续增加：

- 统一 Hover Delay；
- Portal / 层级；
- 屏幕边缘避让；
- Keycap 辅助信息；
- Disabled 原因；
- Keyboard / Gamepad 对应说明。

不要长期依赖浏览器原生 `title`。

### 6. New Game 仍最像网页原型

New Game 当前仍在 `App.tsx` 内用 Preset Card + 图标表达世界预设。

视觉上缺少真实地图 / 游戏内容，是目前最明显的 Prototype 感来源之一。

建议等真实世界截图可用后重做，不要通过增加卡片边框或装饰纹样掩盖问题。

## 架构不变量

后续修改时不要轻易破坏以下规则：

- `Pause > Tool > Workspace > Gameplay` 空间优先级；
- Camera / Weather 共用 Right Edge Flyout 槽位；
- Tool 状态打开 Flyout 时 OperationHints 隐藏；
- Workspace 不与 Utility Toolbar 同时占据底部；
- Tool 不与 Main Dock 同时存在；
- Pause Save / Settings 的 Esc 先回 Pause Menu；
- Archive 的数据层级是 Game Group → Save；
- Save 模式不能切换到其他 Game Group；
- Settings 在 Main Menu 与 Pause 复用；
- Review Scenario 要能确定性进入关键状态。

## 视觉代码注意事项

当前最容易出现的回归不是 TypeScript 错误，而是 CSS 层级问题。

修改时：

1. 不只检查目标页面；
2. 必须跑全部 Visual Review；
3. 尤其检查 1920×1080 下元素是否溢出、遮挡、过暗；
4. 修改全局 Button、Surface、Typography 时重点检查 Main Menu、Pause、Settings、Archive、Tool；
5. 不通过增加 `!important` 解决长期 Cascade 冲突，除非只是短期定位问题。

## 优先级建议

### 近期

1. 确定 Settings / Workspace / BuildingPlacement 最终视觉语言；
2. 建立共享 Tooltip；
3. 引入真实建筑 / 世界 / 存档缩略图；
4. 推广 Tone、材质和动效语言。

### 视觉稳定后

1. 整理 CSS 职责与历史 refine 文件；
2. 把 New Game 从 `App.tsx` 拆出；
3. 清理未使用规则和重复 Token；
4. 增加少量交互级测试，而不仅是截图成功。

## 结论

当前代码足够支撑继续做 UI 设计，不需要为了“重构”暂停视觉工作。

现阶段最大的风险是过早进行大规模 CSS / 架构清理，导致视觉迭代和代码重构同时发生。更合适的顺序是：

**先稳定最终美术与交互语言 → 再做受控代码清理。**
