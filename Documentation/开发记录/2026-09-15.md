# 2026-09-15

## Visual Cleanup Pass 2

在第一轮“文字减法”完成后，开始处理容器、边界、Typography 与视觉聚合。

目标不是继续删除功能，而是减少网页 / SaaS 感，同时避免界面因为过度极简而失去设计层级。

### Settings

- 减少逐行分隔线；
- Select / 数值不再使用重输入框；
- Toggle 只保留开关本体；
- Slider 减少框套框；
- 提高核心参数字号和对比度；
- 保留全屏空间，但避免把控件摊到屏幕两端。

审图结论：方向正确，但后续不能继续单纯删框，需要增加 Tone、材质和空间聚合。

### Building Workspace

- 保留一个主 Workspace Surface；
- 减弱侧栏、筛选条和内容项的盒子感；
- 建筑条目从“网页 Card”转向“游戏内容目录”；
- 提升建筑名与核心属性可读性；
- 暂时用不同线性图标区分建筑，后续应替换为真实建筑缩略图 / RenderTexture。

### BuildingPlacement

- 减少内部摘要 Card；
- Parameter Value 不再逐项套框；
- Segmented Control 减少完整外框；
- 通过对齐、留白和状态色组织层级。

### GameplayOperationHints

进一步收敛为 Shortcut Rail：

- 当前模式；
- 当前主要输入；
- 旋转 / 反转；
- 撤销 / 重做 / Esc 等次级快捷键。

不承担教程说明。

## 当前美术判断

经过减法后，项目已从“信息过密”进入新的阶段：部分界面出现“过于简约、略显单调”的风险。

下一阶段原则：

**信息继续做减法，视觉层级开始做加法。**

优先增加：

- 2%～5% 的明暗 Tone 层级；
- 极弱材质、渐变、内高光；
- Selected / Focus 暖金氛围；
- 真实游戏内容图像；
- 更丰富但克制的排版节奏；
- Hover / Tab / Flyout / Preview 的轻动效。

明确不回退到：

- 说明小字；
- 框套框；
- 装饰编号；
- 大量金边；
- 云纹、卷轴、木纹等仿古装饰。

## Visual Language Pass 3

使用 Settings、Building Workspace、BuildingPlacement 三个代表页面建立新的视觉基准。

### Settings

从单列设置表进一步调整为“一个主 Surface + 两个真实功能组”。

- 左右两栏都承载实际设置项，不恢复无意义 Preview；
- 通过主 Surface、组内 Tone、极弱内高光和 Active 氛围增加层级；
- 当前 Tab 使用暖金微染和轻量下划线聚焦；
- Slider、Select、Toggle 保持轻量控件，不恢复重输入框；
- 参数组保持信息简洁，但不再呈现 Wireframe 式空旷感。

审图结论：方向成立。全屏 Settings 可以丰富，但丰富来源应是功能组、Tone 和空间聚合，而不是额外摘要。

### Building Workspace

将建筑条目正式改为“图像为主、文字为辅”的内容目录。

- 缩略图占建筑条目主要面积；
- 暂时直接裁切项目已有真实游戏截图，而不是生成 AI 建筑图；
- 不同条目使用不同截图和裁切区域，减少纯图标占位感；
- 图标退居缩略图右上角，只作为轻量类型标识；
- 名称与一条核心属性放在底部；
- Hover 使用图片轻提亮、轻缩放、底部暖金细线。

当前真实截图裁切只是过渡方案。最终仍应由真实建筑 RenderTexture / 建筑预览截图替换，不能把当前城市截图裁切当最终建筑素材。

### BuildingPlacement

继续保持工具面板的信息密度不增加，但加强“当前状态正在工作”的感觉。

- Terrain Summary 升级为较明确的状态带；
- Position / Massing / Roof 根据模式切换局部 Ambient Tone；
- 当前参数区增加极弱暖金侧向焦点；
- 参数行与 Segmented Control 增加轻 Hover；
- 模式切换使用短 Fade + 约 5px Slide；
- Tool Dock 的 Active / Toggle / Complete 状态比普通状态更清楚；
- 未恢复任何说明段、重复标题或 Card 堆叠。

审图结论：位置、楼身、屋顶三个状态均保持清楚，面板没有因视觉丰富而变重。

## Workspace Browser Pattern

在继续审查 Building Workspace 后，重新确定所有内容型 Workspace 的统一信息架构：

`Primary Rail + Context Filter + Content Grid`

### Primary Rail

左侧只负责一级内容类别，采用“小型线性图标 + 简短文字”。

建筑当前一级分类：

- 全部；
- 塔；
- 殿；
- 楼阁；
- 屋舍；
- 门；
- 廊榭；
- 特殊。

Selected 使用左侧暖金细线、图标 / 文字提亮和弱暖金 Tone，不再使用旧方案的大方块分类按钮。

### Context Filter

顶部改为纯文字二级筛选，视觉权重低于左侧一级分类。

建筑筛选会随一级形制变化，例如：

- 塔：攒尖 / 楼阁式 / 密檐 / 覆钵；
- 殿：庑殿 / 歇山 / 悬山 / 硬山 / 卷棚；
- 屋舍：悬山 / 硬山 / 卷棚 / 歇山。

这个顶部区域是“上下文筛选”，不是固定屋顶控件。未来围墙、城墙、桥梁 Workspace 可以复用同一位置，但使用自己的结构 / 构件 / 类型词汇。

### Content Grid

第一版将建筑内容从 3 列大 Card 改成 4 列紧凑目录项，以矩形预览为主要视觉。

Visual Review 检查后，导航结构成立，但继续讨论后确认建筑选择更依赖名称与形制文字，而不是截图本身，因此进入下一轮 Text-first 调整。

## Workspace Text-first Pass

Building Workspace 的 Card 改成 **3 列横向短卡**：左侧矩形预览，右侧名称与一条核心属性。

设计结论：

- 建筑名是主要识别信息；
- 预览图用于辅助识别，不应占据 Card 大部分面积；
- 3 列比 4 列更能保证中文建筑名的完整可读性；
- Card 高度压缩到约 88 px，适合快速扫描；
- Header 增加与 Workspace 类型对应的小图标；
- Primary Rail 增加到足够多的示例项，并实现独立纵向滚动；
- Context Filter 保持固定在顶部，筛选项过多时单行横向滚动；
- Content Grid 独立纵向滚动，Header / 左侧分类 / 顶部筛选不随内容移动；
- Prototype 数据扩充到 20 个建筑条目，用实际溢出来验证滚动，而不是只写 `overflow`。

人工审图结论：文字成为明确视觉重点，预览图已退居辅助；3 列密度比此前 4 列更适合当前建筑名长度，滚动区也不会破坏整体 Workspace 层级。

这次调整覆盖此前“图像为主”的临时结论。当前正式基准改为：**文字主导、矩形预览辅助。**

## Workspace Bounded Viewport Pass

继续审图后进一步收紧 Building Workspace 的同时可见信息量。

阶段性基准：

- 主内容固定为 `3 列 × 2 行`，一屏同时显示 6 个建筑；
- Content Grid 可纵向滚动，但第三行不得露出半截；
- Workspace 总高度同步收紧，不通过大面板留空来隐藏多余内容；
- 左侧 `全部` 固定在顶部，作为稳定入口；
- 其余一级类别进入独立滚动窗口，正常只显示约 5 个分类；
- 左栏底部使用弱渐隐提示还有内容，不增加上下翻页按钮；
- 顶部 Context Filter 固定，继续使用纯文字横向滚动。

人工审图结果：主内容只显示完整两行，没有第三行露头；左侧不再一次铺出全部一级分类，Workspace 整体更紧凑，也更接近长期大量内容下的真实使用状态。

这一步随后被“组分页”方案替代；保留本段用于记录设计演进，不作为当前规范。

## Workspace Group Paging Pass

考虑到正式游戏中建筑数量可能非常大，继续使用自由滚动会形成极长列表，也不利于位置记忆与手柄操作，因此将 Building Workspace 从 Scroll Browser 改为 **固定容量的组分页浏览器**。

当前正式基准：

- `全部建筑` 固定在 Primary Rail 顶部；
- 其余一级分类每组显示 5 个，通过底部边缘式上一组 / 下一组控制切换；
- 不显示 `1 / 2`、数字页签或圆点页码；
- 左侧翻组控件由极弱细线 + 左右箭头构成，与整体低噪音视觉一致；
- 主内容每组固定 `3 列 × 2 行 = 6 个建筑`；
- 主内容不再纵向自由滚动，通过左右边缘箭头切换完整内容组；
- 当后面还有内容时，右侧两行各露出一小块下一组卡片缩略图，暗示“还有下一组”；
- 露边被拆成上下两块短卡片边缘，避免连续竖条被误读为滚动条；
- 上一组存在时左边缘同样可出现返回控制与内容露边；
- 内容翻组采用轻 Fade + 数像素横移，保持约 160～200 ms；
- Context Filter 仍保持顶部纯文字，并且不承担主分页职责。

设计理由：

1. 建筑选择属于离散内容浏览，不是连续阅读 Feed；
2. 固定 6 个内容的空间关系更容易记忆；
3. 大量建筑下不会出现越来越长的滚动条；
4. 对手柄、键盘和未来 Unity UI Toolkit 导航更友好；
5. 不显示精确页码可以避免文件管理器 / 网页分页感，只表达“前面 / 后面还有内容”。

最新审图确认无页码分页的整体方向成立，主内容露边已经调整为卡片边缘语义而不是滚动条语义。
